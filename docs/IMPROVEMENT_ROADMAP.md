## Tier 1 — Quick Wins (Low effort, meaningful impact)

These are small code changes or config adjustments with no protocol risk.

### T1.1 — Build statime in release mode + lower log verbosity ⭐ Highest priority

**Status**: ✅ Done (April 2026).

**Impact**: Largest free improvement — PTP jitter reduction 3–5× with zero hardware changes.

Currently `statime-inferno.service` runs `target/debug/statime` (34% involuntary preemptions measured).

#### Why was debug mode intentional?

The `teodly/statime` fork was made for two reasons — both required active validation:

1. **PTPv1 bug fix** (`9f38292`) — upstream statime had a bug in `timestamped-socket` causing poor sync with PTPv1. Dante uses PTPv1. This is the primary reason for the fork; without it sync with the Shure grandmaster was unreliable.

2. **MONOTONIC virtual clock** (`e5f3e87`, July 2025) — standard statime adjusts `CLOCK_REALTIME` to track PTP. This is wrong for audio: NTP can fight PTP mid-stream, causing clock jumps. The fork adds a dual-layer overlay clock based on `CLOCK_MONOTONIC_RAW` and exports it via `usrvclock` Unix socket. Config: `virtual-system-clock = true`, `virtual-system-clock-base = "monotonic_raw"`. This is exactly what Inferno's `ClockOverlay` / `media_clock.rs` receives.

The debug build was used while the new dual-layer clock architecture was being validated — it keeps `assert!` guards active and produces better panic traces if the dual-layer locking fails. The commit message itself said *"looks like pretty stable..."*.

**The feature has been stable for ~9 months** (last stabilising commit `244f20a`, July 18 2025: tightened delay rejection guard 10ms→1ms, changed the unsafe `debug_assert!(time >= filter_time)` to a safe `return`, demoted Kalman filter logs from `info!` to `trace!`). It is now safe to switch to release.

#### Also lower `loglevel` in config

`inferno-ptpv1.toml` has `loglevel = "trace"` — set during debugging of the MONOTONIC clock. In release mode this is a meaningful overhead: trace-level Kalman filter and interclock measurement logs fire continuously. Lower to `"info"` for production use.

```bash
# On dante-doos:
cd ~/statime && cargo build --release

# Update service binary path:
sudo sed -i 's|target/debug/statime|target/release/statime|' \
    /etc/systemd/system/statime-inferno.service

# Lower log verbosity in PTP config:
sed -i 's/^loglevel = "trace"/loglevel = "info"/' ~/statime/inferno-ptpv1.toml

sudo systemctl daemon-reload && sudo systemctl restart statime-inferno.service
```

**Complexity**: Low — config changes only, no code changes. The debug→release switch is now safe.

**Applied config** (no CapabilityBoundingSet — it strips CAP_DAC_OVERRIDE from root and prevents config file reading).

> **⚠️ Cannot use mainline statime (pendulum-project/statime v0.4.0)**: Confirmed April 2026 — neither the PTPv1 bug fix nor the MONOTONIC virtual clock feature has been merged into upstream. The `teodly/statime` fork is still **mandatory**. This item (T1.1) means we built the **teodly fork** in release mode, not that we switched to mainline.

## Tier 2 — Medium Effort, Good DC Visibility

Meaningful features requiring more than trivial code changes but no protocol reversals.

### T2.1 — Audio peak levels (0x8002 block in heartbeat)

**Status**: ✅ Done (April 2026).

**File**: `info_mcast_server.rs` — `send_heartbeat()`

The `get_peaks` callback was already wired in the `Multicaster` struct but was never called. The 0x8002 wire format was reverse-engineered from a live Dante device capture (192.168.1.43, a 2-channel DVS device) with active audio flowing:

```
[u16 block_len][u16 0x8002][u16 0x0004][u16 data_len][u32 counter]
[u16 num_tx_ch][u16 num_rx_ch][u32 reserved=0]
[u16 bits_per_sample][u16 reserved=0]
[u8 × num_tx_ch]  ← TX peak values, 0–255 log-scale
[u8 × num_rx_ch]  ← RX peak values, 0–255 log-scale
[u8 pad if (num_tx+num_rx) is odd]
```

**Format confidence note**: The 0x8002 format was reverse-engineered from device `192.168.1.43`, which is another Inferno-based device (Spotify player), not an Audinate-certified reference device. The format is self-consistent and peak bytes demonstrably vary with audio levels, but has **not been confirmed against a Shure or other certified Dante device**. The real validation is whether DC shows peak meters for dante-doos — if it does, the format is correct; if not, a capture from a certified device sending 0x8002 would be needed.

**Verified**: dante-doos sends 0x8002 in every Packet 1 heartbeat alongside 0x8000+0x8001. TX peaks and RX peaks vary per packet matching live audio (RX: ~170/255, TX: ~75/255 during testing).

**Complexity**: 32 lines added to `info_mcast_server.rs`.

### T2.2 — Real missed-packet counting via timestamp gaps

**Status**: ✅ Done (April 2026).

**File**: `flows_rx.rs`

The `missed_packets` `Arc<AtomicU32>` counter is fully wired and read by DC. Previously it counted packets received *after* their latency deadline — not actual packet loss.

The Dante packet format is `[0x02][u32 secs BE][u32 subsec_samples BE][PCM data...]` — there is NO sequence number field. Detection uses timestamp gaps: `last_rx_timestamp` and `last_frame_samples` are tracked in `SocketData`; on each receive, `expected_ts = last_ts + frame_size` is compared to the current timestamp. If `gap > frame_size / 2`, then `gap / frame_size` packets are counted as missed. Gaps over 5 seconds are treated as stream restarts (no count).

**Complexity**: 25 lines added to `flows_rx.rs`.

## Tier 3 — High Effort, Major Features

Significant development work requiring protocol research or architectural changes.

### T3.1 — AES67 Model 1 (Dante bridge)

**Background**: AES67 is a different wire format from Dante. The key difference:

| | Dante (current) | AES67 |
|---|---|---|
| Header | 9 bytes: `[0x02][u32 secs][u32 subsec_samples]` | Standard 12-byte RTP: V=2, PT=96, seqnum, timestamp, SSRC |
| Epoch | PTPv1 epoch | PTPv2 TAI epoch |
| PTP version | PTPv1 | PTPv2 |

**Implementation path** (estimated 5–10 days of focused work):
1. TX: change header write in `flows_tx.rs:142–147` to emit standard RTP — 2 days
2. RX: update parser in `flows_rx.rs:118–121` to read RTP header — 1 day
3. Codec negotiation: add flow-control protocol changes to accept AES67 flow creation — 2 days
4. Feature flag: only after all above, set `content[0x14] |= 0x04` in `send_heartbeat()` — 1 line

**Critical**: Do not set the AES67 feature flag before the format change — DC will attempt AES67 flow creation and silently fail.

**Complexity**: High. Requires parallel PTPv1/v2 handling and careful interop testing.

### T3.4 — Device reboot via DC ✅ Done (Apr 2026)

**Protocol decoded** from `captures/dante7.pcapng` at `06:47:47.630706 UTC`:

DC (`192.168.1.62`) sends a **conmon-format** UDP packet to the device's `info_request_port`
(standard Dante port 8700; inferno uses `ALT_PORT+3` = 6007/6011):

```
[ffff][length][seqnum][0000][DC_MAC_6B][0000]["Audinate"][outer=073d][inner=0090][0000][0064][0001][0000]
```

At `request_buf[24..32]` (the 8-byte region already matched in `info_mcast_server.rs`):
- `[0x07, _, 0x00, 0x90, 0, 0, 0, _]` = **REBOOT** (conmon message_type `0x0090`)
- `[0x07, _, 0x10, 0x08, ...]` = DC periodic heartbeat query (no response needed)

Inferno already had the unicast socket open on this port (line 490, `info_mcast_server.rs`).
The `0x073d` packets previously logged as "unknown request to multicast port" were these
heartbeat queries and reboot commands.

**Implementation** (commit `b6f483c` on `fix/dc-latency-display`):
- Added match arm `[0x07, _, 0, 0x90, 0, 0, 0, _]`: sends ack `0x0092` to `224.0.0.231:8702`
  (same `device_info_destination`), then calls `std::process::exit(0)`.
- Added match arm `[0x07, _, 0x10, 0x08, ...]`: logs at `trace!` level (silences old warnings).
- systemd `Restart=on-failure` handles re-launch automatically.

**Note**: The earlier analysis was incorrect — `0x1001` is the **CMC register handshake** (port 8800),
not a reboot command. The actual reboot is a conmon packet on `info_request_port` (NOT ARC/CMC ports).
No additional capture was needed; dante7.pcapng already contained the reboot event.

**Root cause of greyed-out Reboot button** (fixed in commit `327008c`): DC only sends the CMC
`0x3010` controller-registration keepalive (which gates all Device Config management buttons) to
devices that respond to `CMC 0x1001` with start code `0x1200`. Inferno was echoing back the
request's `0x1000` start code via `rem.start_code` in `req_resp.rs`. Fix: added
`respond_with_struct_start(RESPONSE_START_CODE, ...)` and a `0x3010` echo handler in `cmc_server.rs`.
Board_info flags (0x17) do **not** control DC button state — this was a false hypothesis pursued
during debugging. The `0x40`/`0x80` bits in 0x17 are informational only.

**Side effect**: the CMC 0x3010 fix also ungreyed the **Switch Config** and **Addresses** tabs in
DC Device Config. These are new open issues (T3.7, T3.8) — clicking them likely sends opcodes
inferno does not yet handle.

**Board_info flag map** (empirically determined by testing):
- `0x15 = 0x7c` — required to keep **Clear Config** greyed; setting `0x00` causes DC to enable it.
  Clear Config sends conmon `0x0077` — inferno handles it as a defensive no-op. Despite 0x15=0x7c
  the button remains clickable in some DC versions; see T3.9 for planned implementation.
- `0x16 bit 0x40` — enables **Addresses** and **Switch Config** tabs; intentionally NOT set.
- `0x17 bits 0x01|0x02` — required companion bits alongside `0x40` (Reboot) for DC to activate
  the Reboot button; removing them greys the button despite `0x40` being set.
- `0x17 bit 0x80` — Factory Reset flag; intentionally NOT set; DC greys the button regardless.

### T3.9 — Implement Clear Config (conmon 0x0077)

**Context**: The Clear Config button in DC Device Config is clickable (despite attempts to grey
it via board_info `0x15`) and sends conmon opcode `0x0077`. Currently inferno logs and ignores it.

**Desired behaviour**: when DC sends `0x0077`, inferno should reset all runtime Dante state it
holds in memory — specifically:
- Clear any stored channel subscriptions / routing assignments
- Reset device name to the default (hostname-derived)
- Discard any cached peer device information
- Do **not** affect the ALSA plugin config or systemd unit files (those are not Dante state)

**Why this is safe**: inferno holds no persistent on-disk Dante config. A "clear" is therefore
equivalent to a soft reset of in-memory state without a full process restart. The user expects
this to match the behaviour of a real Dante device's Clear Config.

**Implementation sketch**:
1. In the `0x0077` match arm in `info_mcast_server.rs`, send a message on the existing channel
   infrastructure to reset subscription state in `flows_rx.rs` / `arc_server.rs`
2. Alternatively, call `std::process::exit(0)` (same as Reboot) — systemd restarts the service
   cleanly, which achieves the same result since all state is in-memory. Simpler and correct.
3. Ack with an appropriate conmon response code so DC knows the command was accepted.

**Recommended approach**: exit(0) + systemd restart — identical mechanism to Reboot, zero risk
of partial-reset bugs. Only diverges from a real device if DC expects state to differ from a
full reboot after a clear config.

**Complexity**: Low if using exit(0); Medium if implementing selective in-memory state reset.

## Tier 4 — Hardware Migration (Long-term)

### T4.1 — PREEMPT_RT kernel on dante-doos

The current mainline kernel has worst-case scheduling latency of 10–50ms. A PREEMPT_RT kernel reduces this to under 100µs.

Expected result: buffer margin reducible from ~2–3ms to ~0.3–0.5ms, approaching Shure MXWANI8 hardware performance. Combined with T1.1 + T1.2, this is the highest achievable PTP quality improvement without hardware changes.

```bash
# Arch Linux:
pacman -S linux-rt linux-rt-headers
# update bootloader, reboot
```

### T4.2 — Migrate to EliteDesk-01 with Intel I219-LM hardware PTP

The RTL8111 in dante-doos has no hardware timestamping. The Intel I219-LM in EliteDesk-01 **does** support `SOF_TIMESTAMPING_TX_HARDWARE`.

Expected PTP offset with hardware timestamping: ±50–200ns (vs current ±500µs–2ms spikes).
Practical min buffer: 0.1–0.3ms (vs current 2–3ms).

Steps:
1. Install `linux-headers` on EliteDesk-01, verify `/dev/ptp0`
2. Update `inferno-ptpv1.toml`: `hardware-clock = "required"`
3. Deploy full Inferno stack

## Statime Fork Reference

The `teodly/statime` fork (https://github.com/teodly/statime) is **not** a cosmetic fork — it contains two essential patches that upstream statime lacks:

| Commit | Change | Why essential |
|--------|--------|---------------|
| `9f38292` | Fix bug in timestamped-socket causing poor PTPv1 sync; retry DelayReq on error | Dante uses PTPv1 exclusively; upstream sync was unreliable without this |
| `e5f3e87` | MONOTONIC-based virtual clock (`virtual-system-clock-base = "monotonic_raw"`) | Prevents NTP from fighting PTP mid-stream; Inferno `ClockOverlay` only works with this |
| `effe92a` | Make `PortTimestampToTime` for `SharedClock` more generic | Required for dual-layer clock type to compile |
| `244f20a` | Tighten delay guard (10ms→1ms), demote Kalman logs `info!`→`trace!`, fix unsafe `debug_assert` | Stability pass on the MONOTONIC clock — final stabilising commit |

**Do not replace with upstream statime** — the MONOTONIC virtual clock is architecturally necessary for Inferno. The PTPv1 fix alone would make upstream unusable with Dante devices.

The fork should be monitored for upstream merges; the PTPv1 fix in particular is a valid upstream contribution.
